## First implementation

[Read-only preflight](../../backend/neon_preflight.py) validates an independently pinned direct Frankfurt development endpoint, hpi_private database, owner, strict TLS verify-full with system roots and required channel binding. It refuses pooled endpoints, unapproved connection options, ambient PG environment settings, unexpected role privileges, server major version or nonempty application target. It uses a read-only transaction, emits only aggregate status and sanitises connection failures. No automatic connection or live workflow. An explicit operator CLI (`python -m backend.neon_preflight`) reads the existing three environment settings and emits aggregate JSON or a generic refusal with nonzero exit. Do not configure an elevated owner secret in this public repository. The expected endpoint is an operator-controlled configuration, not inferred from a branch name or request; no actual host or secret is committed. Tests are offline mocks in the existing PostgreSQL runtime suite. This is only a bootstrap preflight, not a cloud importer or production adapter.

Offline qualification adds a disposable PostgreSQL 17 role with the observed non-superuser privilege shape; canonical migration is tested under that role, not the CI superuser. Historical and runtime disposable guards remain unchanged. This is not a live Neon compatibility claim.

Second offline slice: shared internal canonical/historical migration and reader-grant code is exercised under the observed non-superuser privilege shape, including transactional rollback, repeatable migration, read allowlist, prohibited writes/DDL/temp/buyer-table access and grant drift. Original disposable entry points remain guarded; there is no live provisioning or reader activation entry point. Hosted verification pending.
