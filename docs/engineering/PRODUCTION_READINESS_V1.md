# Production Architecture and Data Readiness V1
**Owner-authorised 24 November 2026.** PostgreSQL is an approved candidate, not a production release. PA1–PA4 synthetic fixtures and CI, PA5–PA7 bounded source research and aggregate audits. No paid infrastructure, deployment, main merge or property-level publication.

## PA1 architecture decision
Retain the React/TypeScript/MapLibre frontend, Python modular monolith and canonical pure matcher. SQLite remains the existing local runtime and is not migrated or replaced. PostgreSQL 17 is a candidate for hosted persistence; psycopg 3.2.9 is pinned for the CI harness only. Use parameterized SQL, transactional migrations, private database network, HTTPS and a managed identity provider (provider not selected). Gunicorn and Render are candidates, not provisioned or approved. No microservices. A public service requires a new runtime/security integration decision, concurrency validation, costs and operator acceptance.

## PA2/PA3 compatibility and recovery
Explicit PostgreSQL v1–v3 scripts translate the frozen SQLite baseline: regex PIN check, BIGINT cents, double precision for existing measurements, BIGINT PIN cast, explicit identity order in shortlist membership. Original SQLite files/scripts are untouched. Checksummed migration history, transactional advisory lock, no adoption of unknown tables, no downgrade. The compatibility harness seeds ONLY canonical invented in-memory rows and reuses existing investigation and shortlist Python services with a narrow static SQL dialect adapter. No HTTP runtime switch or production importer. Validate source seed, compare canonical responses to SQLite including insufficient cases and history, test FK rollback, connection reopen, pg_dump/pg_restore into a separate ephemeral database and tamper refusal. No dump published. Actual process-server restart, real migration of private files, concurrency, pooling, disaster-recovery policy and production schema validation remain unproven.

## PA4 ownership/access design
Separate ownership SQL experiment refuses populated buyer tables rather than silently assigning owners. It adds owner IDs, cross-owner membership foreign keys, row-level security on investigations/results/evidence/shortlists/members. Test two fictional users with non-owner, non-superuser, NOBYPASSRLS role and default deny without identity. Owner context is trusted server-only; test uses controlled session setting, not an authentication system. A production request must validate provider issuer/audience/signature/expiry, map immutable issuer+subject to internal owner, bind transaction-local identity and reset on pool return. Never let clients supply owner IDs or SQL/session settings. Separate migration role, backup role, read-only curated sources and least-privilege runtime. Production writes must acquire shortlist row lock or enforce capacity/distinct parcel in DB under concurrent transactions. Define account deletion/retention, audit without personal payloads, CSRF, session revocation, rate limits, and operational recovery before deployment. RLS is defense-in-depth, not proof of authentication. PostgreSQL docs: https://www.postgresql.org/docs/17/ddl-rowsecurity.html and https://www.postgresql.org/docs/17/app-pgdump.html.
